1. The problem

When a phone loses GNSS (tunnels, urban canyons, multi-storey car parks), the app has to keep estimating position from the phone's own accelerometer and gyroscope. Integrating raw phone IMU twice drifts fast. On our held-out test windows it reaches a median of 28.5% of the distance travelled after 60 s. The problem statement asks for drift below 10%, map matching to real roads, and a model small enough to run on the phone.

We use the IO-VNBD dataset: phone (S) and vehicle (V) CSV logs at 10 Hz with GNSS ground truth. Two data problems had to be fixed before any learning:

  • Clock offsets. Phone and vehicle clocks disagreed by 0.3–116 s. We re-synchronised each phone log by cross-correlating its gyro yaw rate against GNSS-derived yaw rate.
  • Unknown phone mounting. The phone's axes aren't aligned with the car. We estimate the rotation per drive by regressing the phone IMU against GNSS-derived vehicle motion.

Drives are split three ways. Training uses most drives. Validation uses S2 + Vtb5 only: two other validation drives were in the training set of the current checkpoint, so they're excluded from model selection. The test drives Y1, M and Vw4 are touched only for final reporting.

2. End-to-end pipeline

Each stage has one job. The network never outputs a position; it outputs corrected sensor readings. Physics and the filters turn those into a trajectory, which keeps the output physically plausible and lets the map correct it.

3. Model architecture

The network is a residual model. It predicts the phone's sensor error, which is then subtracted from the raw reading. It doesn't predict velocity or position directly. A model that only has to learn corrections starts from a sensible answer (the raw IMU) and generalises better than one that has to learn motion from scratch.

Physics integration (same equations in training and in the app)

Δψ_k = −Σ_{j≤k} ω̂_j · Δt v_k = relu( v0 + Σ_{j≤k} â_fwd,j · Δt ) · (1 − p_stop,k) p_k = p0 + Σ v_k · [sin ψ_k, cos ψ_k] · Δt Δt = 0.1 s

Because integration is differentiable, the losses are computed on the resulting trajectory as well as on the corrected sensor values.

Training objective

  • Velocity-direction loss: minimises the angle between predicted and true velocity vectors, penalising heading drift where it originates.
  • Increment losses on per-step heading change and speed change, weighted by sample (w_speed) so braking and turning segments aren't drowned out by cruising.
  • Speed magnitude and stop losses (p_stop against zero-speed labels).
  • Residual regularisation: keeps ê small and smooth, so the model corrects the sensor rather than inventing motion.

Each training window gets a random destination taken from later in the same drive, with the route between them, so the model learns to use a destination when one exists and to cope without one. On test windows, route input lowers open-loop drift from 18.9% (destination only) to 18.1%.

4. Filtering and map matching

The TFT output is integrated by a 9-state planar EKF. It carries what the network can't know from a single window: the slowly varying biases and the accumulated uncertainty.

StateMeaningRole
E, NPosition (east, north)What the app shows
ψHeadingIntegrated from corrected yaw rate
v_f, v_lForward and lateral speedv_l ≈ 0 enforced by the non-holonomic constraint (NHC)
b_g, b_aGyro and accel biasMade observable by road-heading updates
ds, b_sSpeed scale and offsetAbsorbs systematic speed error

Adaptive NHC. A car doesn't slide sideways, so lateral speed is pseudo-measured as zero. The noise on this constraint grows with yaw rate, acceleration and vibration, with Student-t reweighting of outliers, so it's trusted on straight roads and relaxed in hard turns.

Map matching. 300 particles live on the OSM road graph extracted per drive. Each particle has its own road, arc position, lateral offset and speed-scale error. Once a second each is weighted by:

  • cross-track distance to its road;
  • along-track agreement with the EKF;
  • heading against the road bearing;
  • curvature against the gyro;
  • a large penalty for travelling against a road's direction.

At junctions particles branch in proportion to heading agreement, with a planned-route bonus. The filter decides with a 3 s fixed lag. When confident, it sends a position (and on straight roads, heading) fix back to the EKF, applied at the lagged time and replayed to the present.

6. Where the remaining drift comes from

Once the map fixes cross-track error, almost all remaining error is along-track: the car is on the right road but the estimate is ahead of or behind it. The median along-track error is about 45 m, against 5–7 m cross-track. Along-track error is speed error integrated over time, so we sliced the TFT's speed error by driving condition on the validation drives.

7. What we tried, and what we kept

Every change is an ablation against the same control on the validation drives, with 3 particle-filter seeds. It's kept only if it improves drift without worsening the tail or wrong-road rate. Seed-to-seed noise is about ±0.3–1 point, so small gains are treated as no change.

Next: confidence-aware map corrections

The v2 turn landmark shows the map holds the information needed to fix progress errors, but applied blindly it also makes some outages worse. The confidence layer computes three separate scores:

  • dead reckoning (EKF covariance, speed-scale uncertainty, NHC innovation, TFT residual);
  • map match (cross-track, along-track and heading residuals kept separate, particle effective sample size, cloud spread);
  • decision (best vs second-best road probability).

These map to four actions. High confidence allows the along-track junction fix. Medium confidence softens and clips the fix. Low confidence lets the map only rule out impossible roads, with no snapping. Very low confidence widens the particle search and waits for the next turn.

In unit tests, the policy keeps both hypotheses alive on genuinely ambiguous parallel roads 82% of the time, against 55% for the current filter. It changes nothing when switched off: tracks are identical to the validated pipeline on real outages.

8. Deployment

  • Exported to ONNX (opset 17, 3.8 MB), with a manifest listing input layout, feature order, normalisation statistics and filter configuration.
  • ONNX Runtime must use ORT_ENABLE_BASIC. The higher optimisation levels contain an operator-fusion bug (onnxruntime 1.29) that corrupts this model's outputs by up to 0.6. With BASIC, outputs match PyTorch within 2.3 × 10⁻⁶.
  • The app asserts the optimisation level at startup and runs four stored real windows as a self-check. A CI test compares PyTorch and ONNX on random and real inputs.
  • The EKF and particle filter are plain NumPy-level arithmetic (300 particles, 1 Hz map step) and port directly to the app.

9. Limitations

  • Map-aided figures cover outages on mapped roads. Off-map driving (car parks, private roads) falls back to TFT + EKF, which is about 18% open loop.
  • The test set is three drives, so seed-to-seed and drive-to-drive variation (±0.3–1 point) is similar in size to many candidate improvements.
  • Normalisation statistics differ slightly from those the checkpoint was trained with (two validation drives were included then). The effect is small and documented.
  • The median target is met; the tail (p90 of 40–50%) is not yet good enough for turn-by-turn guidance through long outages.
